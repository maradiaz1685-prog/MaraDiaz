# Alcance: solo esta carpeta

Este repo (`C:\maradiaz`) es un proyecto de cliente independiente. Cuando se trabaja acá:

- No leer, editar ni operar sobre archivos de otras carpetas de proyecto del usuario (`C:\ofertas locales`, `C:\rifalocal`, `C:\descuentolocal`, `C:\pinogalant`, `C:\tiendalopez`, `C:\localwebone`, `C:\InfernoHost`, etc.). Cada carpeta es un sitio/cliente distinto con su propio repo — no mezclar.
- **git push de este repo NO se puede hacer desde una sesión de Claude Code cuyo working directory principal es otra carpeta.** El clasificador de seguridad resuelve el push contra el repo del working directory principal de la sesión, no contra el remote real configurado acá — el push queda bloqueado con un falso "repo mismatch" sin importar la cuenta de GitHub logueada, y tampoco funciona vía `mcp__github__push_files` (ese conector no tiene auth configurada en esta sesión). Esto se probó a fondo el 2026-07-11: intentos directos de `git push`, reintentos tras `gh auth login`, y el push por API — los tres bloqueados/fallidos por motivos ajenos a la cuenta de GitHub. No perder tiempo reintentando ninguno de los tres desde una sesión de Claude Code — pedirle directamente al usuario que lo haga él.
- **Para pushear:** el usuario tiene que correr `git push` él mismo, desde su propia terminal en su perfil real de Windows. Hay un acceso directo en su escritorio: **"Subir MaraDiaz.bat"** (`cd /d C:\maradiaz && git push origin main`).
- **Causa real del 403 que costó horas resolver (2026-07-11):** NO era un problema de qué cuenta de GitHub estaba logueada en el navegador, ni de `gh auth login/switch` (el usuario no tenía ninguna cuenta logueada en `gh` en su máquina real — "not logged in to any hosts" — y el push igual fallaba). La causa era una credencial vieja **cacheada directamente en el Administrador de Credenciales de Windows** (`git:https://github.com`) con la cuenta equivocada (`nacholaine03-cell`, de otro proyecto que el usuario maneja en otro navegador), y git la usaba sin importar el estado de `gh` ni del navegador. Solución: el usuario abrió el Administrador de Credenciales de Windows (buscar "Administrador de credenciales" en el menú inicio) → pestaña "Credenciales de Windows" → borró la entrada `git:https://github.com`. Al pushear de nuevo, git pidió usuario/contraseña frescos en la terminal — ahí usó usuario `maradiaz1685-prog` y como contraseña un Personal Access Token generado en GitHub (Settings → Developer settings → Personal access tokens → Tokens classic → scope `repo`), porque GitHub ya no acepta contraseña de cuenta para git por HTTPS. Una vez autenticado así, Windows debería cachear la credencial nueva y los próximos "Subir MaraDiaz.bat" deberían andar directo sin volver a pedir nada — si algún día vuelve a fallar con 403 hacia una cuenta equivocada, es este mismo problema del Administrador de Credenciales, no un tema de `gh` ni del navegador.
